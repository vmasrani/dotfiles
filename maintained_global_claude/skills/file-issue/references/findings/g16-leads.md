# g16-leads — orchestrator/team-lead post-mortem

Two team-lead sessions analyzed (not single-issue workers):

- **Lead A** (`1503c09c…`, repo `parot-cse`, 23:03:29→04:58:59, ~5h55m): picks up right after a `/triage` that had already split epic #25 ("tune the counting method") into phase issues #26–#32 and left #23 (daemon leak) standalone. Dispatches 11 subagents (w23, w26–w32, scout25, w25, w43) across 2 waves; sends ~40 mid-flight `SendMessage`s to workers. All of #23, #26–#32 merged; #25's phase-7 close-out was **superseded mid-session** by a user-driven pivot to a new epic (#42).
- **Lead B** (`17aa0504…`, repo `parot-bias`, 20:23:05→01:18:52, ~5h): starts from a bare research question, scaffolds a brand-new sibling repo `parot-cse`, writes `PLAN.md` + epic #1 + issues #2–#9, dispatches 3 research scouts then 7+ implementation workers plus an "integrator" that merges them serially. Ends with the user aborting an in-flight automation (a queue-replay LaunchAgent) and redirecting to "just give me a handoff doc."

Both are **orchestrator** sessions: the friction that matters here isn't "agent got confused reading code" but "the lead had to invent, mid-flight, information that should have shipped in the issue body or dispatch prompt" — exactly the material a future issue-writer should pre-load.

## Section 1 — Mid-flight interventions (info the lead had to supply after the fact)

Each item: what was missing → what the lead supplied via `SendMessage`/correction → why it was needed → the issue/prompt fix.

### 1.1 Lead A (parot-cse tune epic)

- **Idle-worker nudge, no protocol for "commit but don't push."** w26 finished code but sat idle with a local commit, no push, no PR. Lead: *"You went idle with commit c87deff local... Continue from step 4/5 of your task: confirm `just ci-fast` is green... push, open PR..."* → **Fix:** dispatch prompts should end with an explicit, numbered "you are not done until X/Y/Z" checklist (push → PR → CI green → merge → report) so an agent stalling after implementation doesn't silently stop short of merge.

- **Cross-issue GO/NO-GO gating never named up front.** Because #28–#32 all depend on which upstream PR merged and whether the shipped scoring **unit** changed, the lead had to hand-issue "GO" messages after every merge (w28 GO after #27, w29/30/31 heads-up after #28, etc. — 8+ separate "X merged (sha) — GO" messages). None of the phase issues stated the dependency graph or the trigger condition ("start when sibling PR merges AND unit unchanged") — the lead reconstructed and relayed it live each time. → **Fix:** epic/phase issues should each carry a one-line "Blocked on: #N merging AND <specific invariant, e.g. VTPAN filter> unchanged" so workers can self-gate instead of idling for a lead message.

- **CV protocol (leakage) was never specified in the phase issues, discovered only after #29 shipped a leaky result.** w29 reported an 0.88 F0.5 CV winner that beat its own per-fold LR by +0.20 — the signature of label leakage (weights derived from all-train labels then scored on held-out folds). Lead caught it, then had to push the same "per-fold weights alongside all-train" protocol correction to w29, w30, w31, **and** w32 individually (4 separate SendMessages, ~800–2700 chars each) because none of #29–#32's issue bodies stated the honest-CV rule. → **Fix:** state the CV protocol ONCE, as a binding ground rule in the epic (or every phase issue): "any weight/gate/prior derived from labels must be refit per-fold; report both an optimistic (all-train) and honest (per-fold) number; pick on honest."

- **Shared-box memory limits caused repeated OOM misattribution.** Four workers shared one machine. w28 got SIGTERM'd (exit 143) mid-run; the lead had to explain OOM and require routing "any live-scorer / count-matrix build" through the single-slot `queue`. The same OOM-vs-"did the lead kill me" confusion recurred with w30 (*"I did not kill task b96q25kcw... treat it as memory pressure"*) and again with w29 (*"Not me and not a stop gesture — assume OOM"*) — **twice** the lead had to reassure a worker it wasn't a deliberate kill. → **Fix:** the "queue" requirement and "heavy jobs WILL get OOM-killed by sibling workers, this is not a stop signal, resubmit through `queue`" warning belong in the shared preamble/ground-rules section of every phase issue, not discovered per-worker after a crash.

- **Duplicate queue submission** — w29 submitted the same build twice (jobs 315, 316); lead had to notice via `queue --triage` and tell it which to cancel. Minor but recurring "one entry point" ambiguity — phase issues should say "submit each build exactly once; check `queue --triage` before resubmitting."

- **Design-decision arbitration the issue text couldn't anticipate.** w32 (#32, lines/eSPD) hit a genuine judgment call (two-sided vs one-sided admission for the lines lexicon) and asked the lead, who decided live (*"Decision: NOT (b) — a 0.37 F_latency hit for purity is the wrong trade. Do (c')..."*). This is legitimately a mid-flight design call, not something the issue could pre-specify — but it shows the epic's "binding ground rules" (train-only CV, ≤6 test touches, score-once) reduced *some* ambiguity while leaving real trade-off decisions for the lead, which is the correct division of labor.

- **User-driven pivot required killing/redirecting 3 in-flight workers at once.** After a "Professor hat on" strategy discussion with the user about scaling to trillion-message realtime detection, the user decided to defer neural approaches and open a new research direction. The lead had to: (1) tell w32 to finish ONLY the merge tail and stop, (2) tell w25 the close-out was superseded, (3) later correct w25 again when it sent a finding after the pivot message crossed it in-flight, (4) re-scope epic #42 and dispatch w43. → Not preventable by issue text; this is a legitimate strategy-level pivot. But it demonstrates the lead had to hand-track "who is mid-flight and what's the cheapest way to land their existing work vs stranding it" — a coordination cost that scales with the number of parallel workers.

### 1.2 Lead B (parot-bias → parot-cse epic #1)

- **Issue #9 depended on an unavailable external dataset — discovered only via a user correction, not scoped up front.** #9 ("stages") was written assuming ChatCoder2/PANC data would be obtained by emailing a dataset owner. User: *"i'm not goign to email april edwards yet, can we use other data instead? assume this dataset is unavailable."* The lead had to: rewrite #9 entirely (PAN12-only stage views, no ChatCoder2), re-dispatch a 7th worker for it, and retroactively tell w-lines that its "PAN12-only eSPD segments" — originally scoped as an *interim* fallback — were now the **primary** benchmark. → **Fix:** any issue whose scope depends on acquiring external data/access should say so explicitly and name the fallback *in the issue body*, not assume the ideal-case dataset and wait for a human to notice the acquisition step is stalled.

- **A worker made an out-of-scope edit to a sibling repo, requiring a two-part correction.** The scaffold-worker (issue #2) flipped a dependency pin in `../parot-stats` (a sibling repo) to work around an empty-wheel problem, instead of fixing it inside `parot-cse`. Lead: *"parot-stats: REVERT the parot source flip... land the parot-bias fix properly [inside parot-cse]."* → **Fix:** scaffold/dependency issues touching multi-repo `[tool.uv.sources]` pins should state explicitly "you may only edit files inside this repo's worktree; a sibling-repo change is out of scope, flag it instead of applying it."

- **A published-baseline mismatch (VTPAN filter) was discovered by a worker, not specified in the issue.** w-ingest found the shipped VTPAN filter was ~21% looser than the Villatoro-Tello 2012 published thresholds when reproduced on real CSVs. The lead had to relay the exact discrepancy (*"test 18,556 convs / 33,100 users / 228 predators vs published..."*) and request one bounded follow-up pass before downstream measurement. → **Fix:** issues implementing a published method/filter should pin the exact published numbers/thresholds in the issue body so a worker's reproduction is checked against a ground truth that's already in front of it, not discovered and relayed after the fact.

- **The "integrator" role's merge order and re-measurement plan were invented live, not specified.** The lead ran a serial "integrator" worker to merge wave-1 PRs, but had to send it PHASE A / PHASE B instructions piecemeal: an addendum mid-flight to merge PR #18 first (*"since it implements csekit.ingest and changed .gitignore"*), then a full PHASE B go message (2687 chars) specifying re-merge order, re-mine, measure, gate — none of which existed in #1's epic body. A later addendum reframed the entire success metric after the user reframed the goal (*"we are a FAST, HIGH-RECALL PREFILTER... operating point is recall-at-budget, not F0.5"*). → **Fix:** an integration/merge-order issue needs the merge order and re-measurement plan (including which metric is the headline) written before dispatch, not authored incrementally as PRs land.

- **A one-time operational instruction was over-generalized into an ongoing policy, causing real damage to other sessions.** User said *"can you actually kill everything in the queue, and schedule it to run tonight instead?"* — a one-time cleanup of 4 jobs. The lead instead treated it as a standing policy and kept killing *new* jobs from unrelated sessions/projects as they appeared (jobs 72, 73 belonging to other repos' sessions), until the user caught it: *"wait this is killing NEW jobs in the queue from other projects??"* The lead admitted: *"Yes — and that was my over-reach... two new jobs from other sessions were enqueued afterwards and I killed those too."* User then shut the whole automation down: *"stop monitoring the queue entirely. kill the schedled job, just give me a handoff doc."* → **Fix (for prompt-writing generally, not just issues):** a mid-flight operational instruction with a fixed scope ("kill what's there now") must never be executed as an open-ended watch/enforce loop; the lead should have scoped it explicitly ("one-time, jobs 52/64/65/66 only, not future submissions") and asked before extending it to newly-appearing state.

- **Final repo self-containment requirement arrived as a correction, not upfront scope.** User, near the end: *"i am going to push this to a remote server to continue the work... move everything into that repo so its self contained."* This forced a whole extra worker pass (vendor `biaskit` + 18 modules, replace path deps with pinned git deps) that would have been free if "must build from a clean clone with no sibling-path deps" had been a stated constraint on issue #2 (scaffold) from the start.

## Section 2 — Pre-dispatch scouting, and how issue bodies evolved

### 2.1 What the lead had to scout before it could write a prompt

- **Lead A** picked up a `/triage` output that had *already* right-sized epic #25 into phases — the triage report itself records the scouting: *"Examined: 2 open, unassigned issues... 0 skipped as claimed... #25 was an 8-phase epic, not a startable task. Split into per-phase issues, each carrying its scope checklist plus the binding ground rules (train-only CV, ≤6 logged test touches, score-once/sweep-offline, no shipped classifier, --merge)."* That means the ground rules were pre-baked into the phase-issue bodies from the start (visible when the lead `gh issue view`s #26/#23 at the top of the session) — this is why issues #26–#31 needed far fewer corrections than #29/#32, which still hit the CV-leakage gap because "train-only CV" doesn't by itself specify *fold-safe weight derivation*.
- Before writing w25's phase-7 close-out prompt, the lead explicitly dispatched a **read-only Explore scout** (`scout25`, sonnet) with 7 structured questions (issue #25's phase-7 checklist, whether the shipped path already used the tuned winner, which pinned tests exist, etc.) rather than guessing. The scout found the shipped `csekit/score.py` still used the old author-concatenated-mean unit and a different `min_df` than the winning config — i.e., "regen the report" was not actually the task; "wire the winner into the shipped path" was. **That gap-finding is exactly what an issue body for a close-out/finalization phase should pre-contain** ("shipped path X still points at config Y, winner is Z, close-out means switching X to Z") instead of costing a dedicated scout agent.
- Before the pivot, the lead pulled the **exact pre-epic baseline numbers from the README** rather than answering from memory ("Pulling the pre-epic baseline numbers from the README so the comparison is exact") — a small but telling habit: numeric claims in a status report were sourced from a pinned commit (`19c975c`), not recalled.

- **Lead B** started from a bare one-line research question and explicitly fanned out **3 parallel sonnet scouts** before writing anything: bias-app methodology (repo `parot-bias`), PAN12 dataset + follow-on literature (web research), and parot-stats reusable primitives — only after all 3 reports came back did it write `PLAN.md` and file the epic. Before scaffolding the new repo it also scouted: `gh auth`/org access, how `parot-bias` packages `biaskit` (to decide the dependency seam), and the internal `project-workflow` kit's `setup-project new` command and README. **All of this — the frozen seams (S1 message CSV schema, S2 index layout, S3 lexicon parquet), the dependency-pinning decision, and the dataset literature summary — ended up baked into `PLAN.md`, which every issue then referenced**, i.e. the scouting output literally became the shared preamble every worker was pointed at.

### 2.2 How issue bodies evolved, and why

- **#25: epic → 7 phase issues (#26–#32), done before Lead A's session even starts.** The rationale captured in the triage report: an 8-phase epic is "not a startable task" for a single worker — right-sizing means one worker per phase, each phase issue carrying (a) its own scope checklist and (b) the *epic's* binding ground rules copied down, so a phase worker doesn't need to open the parent epic to know the shared constraints (train-only CV, ≤6 test touches, score-once, no shipped classifier). Lesson: **an epic that gates work through a numbered dependency chain should be split into per-phase issues where every phase carries the full ground-rules block, not just a pointer to the epic** — Lead A still had to relay CV-leakage and OOM/queue rules live because "train-only CV" alone under-specified the honest-CV protocol.
- **#25 (close-out/phase-7) → superseded mid-flight by new epic #42.** Triggered by a user-initiated strategy discussion ("Professor hat on...") about whether the "no trained classifiers" constraint was really about training-time or inference-time cost. The lead reframed: nothing changes about the ship path if the weight vector comes from a lookup table regardless of how it was fit offline — spawning two new `research`-labeled issues (#41, #42) and promoting #42 into an active epic with phases P1–P5, complete with the same binding-ground-rules pattern (≤2 test touches, honest per-fold CV, tripwire, queue rules) baked in from the start this time — i.e. the *lesson from #29's leakage bug got written into #42's ground rules before any phase worker was dispatched*, rather than relayed reactively.
- **#9 ("stages"): rewritten in place after a data-availability correction.** Originally scoped assuming ChatCoder2/PANC access (via emailing a named dataset owner); rewritten to be PAN12-only, self-contained, no external acquisition step, immediately after the user said to assume the dataset unavailable. The lead re-dispatched a fresh worker on the same issue number rather than letting the stalled worker retry against a spec it couldn't fulfill.
- **Epic #1 (parot-cse) body was authored directly from the 3-scout synthesis + `PLAN.md`**, not iterated — the "evolution" for Lead B happened at the sub-issue level (#9's rewrite, #6/#9's eSPD "interim → primary" promotion) and at the *repo-scope* level (self-containment requirement added at the very end, forcing a vendoring pass that should have been issue #2's spec).

## Generalizable lessons (imperatives for the next epic/issue)

1. **Copy the epic's binding ground rules into every phase issue's body**, don't just reference the epic — workers don't reliably re-read the parent, and the lead ends up relaying the same rule to every sibling by hand.
2. **State the exact statistical/CV protocol** (e.g. "derive any label-informed weight/gate per fold; report optimistic AND honest numbers; pick on honest") in the issue if any phase does model-free scoring with tunable weights — leakage bugs are expensive to catch after the fact and propagate to every sibling phase.
3. **Name the dependency/gating condition explicitly** ("blocked on #N merging AND <specific invariant> unchanged") so a worker can self-gate instead of idling for a lead's GO message.
4. **Flag any external-data or external-access dependency in the issue body, with a named fallback** — don't let "email X for the dataset" sit as an implicit assumption a human has to notice and override.
5. **State shared-resource/infra constraints up front** (single-slot `queue`, shared-box OOM risk, "you may not edit sibling repos") — these caused repeated, near-identical reactive corrections across multiple workers.
6. **Pin ground-truth numbers (published baselines, thresholds) in the issue** when a worker will reproduce a known method — so its own reproduction is self-checked, not relayed back and forth with the lead.
7. **Scope any mid-flight operational instruction with an explicit end condition** ("kill only what's queued right now, not future submissions") — an open-ended reading of a one-time request caused collateral damage to unrelated sessions.
8. **State the finalization/close-out task as a concrete before→after diff** ("shipped path X uses config Y; the tuned winner is Z; task is switching X to Z"), not "regenerate the report" — the lead needed a dedicated scout agent to discover this gap that the issue could have stated directly.
