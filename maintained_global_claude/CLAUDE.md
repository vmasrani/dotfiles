# Context budget — 86% of spend is carrying context, not generating it

Every token in context is re-read ~43× at 0.1× input price. On Opus that makes a context token cost ~$31/MTok effective vs $5 base — a **6× amplification**. Context grows 92k (msgs 0-24) → 225k (msgs 100+) and never comes back down; 72% of spend lands in sessions longer than 100 messages.

- **`/clear` between unrelated tasks — the break-even is ~5 messages.** A fresh session costs ~40k up front then ~4k/msg; continuing a 220k session costs ~22k *every* message. If >5 messages of work remain and the history isn't load-bearing, clearing is strictly cheaper. Hand off via the issue/PR, not by keeping the session alive.
- **One session, one task.** A session that has changed subject has already paid for the old subject on every turn since.
- **Cheapest token is the one never read.** Before any tool call that returns bulk text, ask what the smallest sufficient slice is.

# Context files — progressive disclosure

Some projects have `*-context.md` files generated by `/research`.

**DEFAULT FIRST ACTION**: run `ctx-index . --depth 1` when starting work in any project (skip only for a single targeted edit the user pointed you at). Then `ctx-peek {dir} 8` for the 1-3 dirs that matter; read a full `*-context.md` only when you need gotchas or entry points.

Other commands: `ctx-tree` (fallback when no context files), `ctx-stale` (find outdated), `ctx-reset`, `ctx-skip [dir] [reason]`.

Rules: never load more than 2-3 full context files at once; if `ctx-index` returns nothing, fall back to `ctx-tree`; if stale, suggest `/research`.

# Code navigation — prefer LSP

When LSP plugins are enabled, prefer LSP tools (`definition`, `references`, `diagnostics`, `hover`, `symbols`) over grep/glob. After every file edit, check LSP diagnostics and fix any errors introduced in the same turn.

- **Never re-Read a file already in this session's context.** It is still there. If you edited it, Edit/Write would have errored on failure — re-reading to "verify" is pure waste. Re-read only when an *external* process changed the file.

# Overall guidelines

- always search for the latest modern libraries and use them when writing code; never write a function yourself when a library provides it

# Fail loud — never write slow defensive fallbacks

**There is ONE correct (fast) path. When it can't run, stop with a loud, actionable error — NEVER silently fall back to a slow, degraded, or wrong path.** Applies in every language. A silent fallback turns a visible failure into an invisible one; prefer a crash over a plausible-but-wrong result.

- **The fast path is the only path.** Delete old slow implementations; don't leave them reachable as safety nets. Delete env vars/flags that silently re-enable a degraded mode.
- **Failures error loudly** (nonzero exit / raised exception / `Err` / thrown error) with an actionable message naming what failed and how to fix it. Never return unfiltered, empty, partial, or wrong-but-plausible results.
- **Validate invariants up front** — fail before doing work, not mid-flight.
- **Stub the not-yet-implemented loudly** — explicit "not implemented" error, never a fall-through to an older path.
- **A test that cannot run is SKIPPED VISIBLY** (`#[ignore]` / `pytest.skip` / `t.Skip`), never quietly passed. "Skipped" and "passed" must never be the same observable state.
- **Nuance:** a legitimate absence (`NotFound`, empty `Option`) may return quietly — that's a correct answer, not a fallback. The test: "could the caller mistake a failure for success?" If yes → fail loud.
- **No try/except / try/catch for control flow.** Let errors propagate. Catch only to add context and re-raise, or at a genuine top-level boundary (CLI entrypoint, request handler).

# Fable is an orchestrator — Fable NEVER writes code

**HARD RULE — when the session model is Fable, Fable NEVER writes, edits, or patches code — not scripts, not tests, not one-line fixes, not code smuggled through Bash heredocs. ALL code is written by opus/sonnet/haiku subagents (Agent tool or Workflow `agent()`).** Fable scopes, researches, designs, writes precise self-contained prompts, dispatches subagents, reviews their diffs, and integrates. Fable may still directly write non-code text: plans, prompts, reviews, documentation, commit messages, memory/context files.

# Delegate context-heavy reads — applies at every session model

Subagents start at ~34k and stay small; the main session sits at 175k. Anything that **reads a lot and returns a little** belongs in a subagent — the bulk never enters your context, and you never pay to re-read it.

- **Always delegate:** CI log triage (`gh run view --log-failed`), test-failure diagnosis, cross-worktree file scouting, "which file does X", doc/API research.
- **Parallel by default.** Dispatch independent subagents concurrently and pre-stage work while they run. The bar is "could this run concurrently?", not "was I told to parallelize?".
- **Verify, don't trust.** Subagent self-reports are claims, not evidence. For load-bearing work, verify yourself: `git status`/`git diff`, build, run the FULL suite (not the agent's chosen subset).
- **Prefer a fresh agent with a self-contained prompt over a fork** — a fork inherits your whole 175k context and saves nothing.
- **Close out idle agents** with `TaskStop({task_id: "<agent-name>"})` when their thread is genuinely closed; sweep at the end of any turn that spawned agents. But don't stop an agent whose context you might still want — `SendMessage` reuses its research; respawning pays for it again. Idle agents don't burn tokens; this is roster hygiene, not cost saving.
- **Default known-slow commands to `run_in_background: true` up front** — don't wait to hit the 2-minute cap first. Applies to every Bash call, mine and any subagent's: full test suites, `cargo`/`just` build-and-test recipes, `queue`/`testq` invocations, CI watches (`gh run watch`), anything with a "queue wait + suite time" shape. There is no auto-background setting in Claude Code (checked 2026-08-14) — this is a standing habit, and it must be stated explicitly in delegation prompts to fresh subagents since they don't inherit it from this file being in *my* context.

# Rust builds — the job queue (`queue`)

**Always add the prefix yourself** on `cargo test|nextest|bench|miri` and `just test*|bench*|ci-fast|ci-deep` — nothing rewrites your command; a PreToolUse hook only DENIES the unqueued ones. `queue X` behaves exactly like `X`: it waits for a free slot (`QUEUE_SLOTS`, default 1), then streams live output and returns the command's own exit code. Leave `cargo check|clippy|build` and `just lint*` unqueued — not queueing them is what keeps them instant.

- **`queue cd /repo && cargo test` is WRONG** — the shell splits on `&&` first, so only the `cd` gets queued. Pass one quoted string: `queue 'cd /repo && cargo test'`.
- **A pause before output is the QUEUE, not a hang.** Check `queue -l`; never re-run to "work around" a slow start.
- **Run long suites detached** (`run_in_background`) — queue wait + suite time routinely exceeds the 10-minute shell cap.
- **`| tail` destroys the exit code** — read `queue --exit-code --last` before claiming a suite passed.
- **Agents write, the lead builds.** Subagents edit code; ONE process compiles and runs the suite.
- **Drop a queued job with `queue --cancel <id>`, NEVER bare `ts -r`** — bare `ts` talks to task-spooler's default socket, not the queue's, so the removal targets a daemon that never heard of the job and fails with "cannot be removed" (looks like a stuck job; it's a misaddressed one). `--cancel` refuses running jobs and prints the exact kill command instead.
- **Before debugging a crowded queue, run `queue --triage`** — report-only; flags duplicates (with the `--cancel` lines to run), same-target-dir overlap, and queued clippy/check-class jobs that should never have been queued.
- **Short jobs may jump long ones automatically** — a queued job with a measured median jumps ahead when everything in front has a median ≥3× its own (once per job, ever). Reordering in `queue -l` is the scheduler working, not a bug. History is keyed per REPO (git common dir) + command, so fresh worktrees inherit siblings' timings.

Flags, `--solo`, the slots model, coalescing, SJF details, and the settled don't-re-investigate list live in `~/dotfiles/maintained_global_claude/queue-reference.md` — read it only when you need it.

# Evidence discipline — a green is a claim, not proof

These rules target failures that produce confident, plausible, wrong output instead of an error. Some are hook-enforced; the hook's presence doesn't excuse the habit.

- **Reconcile the test COUNT against an explicit baseline every run** (e.g. `main @ 4ee8817 = 1502`). A count that goes DOWN without deletions means the binary doesn't contain your code — force a rebuild.
- **Never read a summary line as proof.** Grep explicitly: `rg -n 'FAIL|test run failed|^error'`.
- **Never pipe a test or build run** — `cmd | tail` exits with tail's status. Capture in full, and **end the command with the run's own status, never with an `echo`**:

      <cmd> > /tmp/run.log 2>&1; rc=$?; echo "exit=$rc" | tee -a /tmp/run.log; exit $rc

  The older form of this rule, `<cmd> > log 2>&1; echo "exit=$?"`, prints the right number but leaves the SHELL exiting with `echo`'s status — always 0. Harmless in the foreground, where you read the printed line. **Silently wrong with `run_in_background`, where the task-completion notification has only the process status** and will announce "exit code 0" for a run that failed. The trailing `exit $rc` is the entire fix; wrapping in `( … )` does not help, since a subshell also exits with its last command. This bit three background `ci-fast` runs in one session, each reported as passing while its log said `CI_FAST_EXIT=1`.
- **A background task's reported exit code is the wrapper's, not the command's.** Never accept it over the log. Grep the log for both the status line and the failure patterns.
- **Then extract from a captured log with `rg -n 'FAIL|error'` — never `cat` it, never Read it whole, and never read the same log twice.** A captured log is a file on disk you can re-query with a command; it is not something to park in context.
- **Verify a test filter selected what you think.** A pass over zero tests is a pass. Prefer positional filters; with `-E` expressions, confirm a non-zero expected count first.
- **Anchor the working directory.** Absolute `cd` at the head of every build command, or prefix `pwd &&`.
- **A conditional action needs a conditional marker.** `git commit; echo done` prints the marker even when nothing committed. Compare `git rev-parse HEAD` before/after, or guard: `git diff --cached --quiet || git commit`.
- **Re-run the full suite on the MERGED result** — per-branch greens don't cover the combination.

# Workflow defaults

- **TDD is the default** for any non-trivial change: exhaustive failing-test suite first (happy path, edge cases, boundaries, failure modes, the real-world input that triggered the bug), then implementation, then a full-suite verification pass.
- **Verbal plan approval counts.** If ExitPlanMode is rejected but the user says "proceed" / "go ahead", start executing immediately.
- **Use git worktrees for non-trivial implementation work.** For path-dep'd sibling repos, create matching worktrees under one parent dir so relative deps resolve.
- **Never build in, or `cp` out of, a tree another session has uncommitted work in** — check `git -C <tree> status --porcelain` first. Relocate changes with `git stash` / `git diff | git apply` scoped to files you actually modified.
- **Git cleanup is local-only by default.** Never delete remote branches or unmerged work unless explicitly told.

# GitHub projects — issue → worktree → PR → CI

Projects carrying the workflow kit (markers: `.agent-workflow/AGENT_WORKFLOW.md`, `ci-fast`/`ci-deep` recipes in the justfile) follow this protocol BY DEFAULT — don't wait to be told:

- **Lifecycle:** one GitHub Issue owns one branch, one worktree, one PR. Branch from `dev`, target `dev` (main is for release tasks only). Use the skills: file → `/triage` → `/start-task` → work → `/open-pr` → `/check-pr` (repair red CI) → `/finish-task`.
- **One issue per INVARIANT, not per instance.** Search open AND recently-closed issues before filing; if the invariant is tracked, add your instance to that issue. When what you tripped over is one violation of a rule the codebase should enforce everywhere, sweep for the siblings (`rg -n -m 40`) and file the rule with the inventory. Four issues titled for four symptoms that share one rule are four branches, four PRs, four CI runs, and four reviews for one fix.
- **Review findings become ONE hardening issue with a checklist** — never one issue per finding. Title it for the PR the review covered.
- **A bug-fix PR says class or instance.** Default is the class: show the sibling sweep, or name the test that fails on the next instance. Instance-only is allowed when stated explicitly and the class is filed — never silently. A fix that lands for one filename and leaves the defect for every other filename comes back as a new issue days later.
- **Filed ≥3 issues you didn't start with? Run `/triage` before starting any.** It dedups by invariant, rewrites instances as classes, applies `fast-lane` by predicate, and emits the `/start-task` batches. Issues started one at a time each pay the full lifecycle; triaged together they get batched.
- **Fast lane for `fast-lane`-labeled issues (default, every kitted project).** The label is granted at triage — a SEPARATE ACT (`/triage`) over 2+ filed issues, before any branch exists for them, by the four-part predicate in the kit's policy (≤3 known files; no new interface/schema/dependency; acceptance is an existing check or one assertion; independent of the filing session's design work). Never label an issue whose branch you hold, and never label a lone issue to lighten ceremony for work already underway. Labeled issues may be batched 2-4 per branch/worktree/PR: `/start-task 12 14 17` starts the batch on a `batch-12-14-17-<suffix>` branch, claims by assigning each issue plus ONE comment on the lowest-numbered issue (no per-issue claim comments), each issue lands as its own commit (per-issue revert/bisect survives), and the PR body carries one `Closes #<n>` line per issue plus a per-issue checklist. If a batched issue turns out non-mechanical, eject it: drop its commits, remove its label, unassign, comment why, finish the rest (an ejected issue returns to the strict lane, separate-review merge included). Green `ci-fast` and green PR checks still gate everything; the author self-merges on green per "Who may merge". Unlabeled or design-y work stays strict one-issue-one-PR. Canonical rules: the kit's `AGENT_WORKFLOW.md` (policy-version stamp on line 1); a project opts out only via its own `CLAUDE.md`.
- **Chore lane — work too small for an issue.** A formatter run, lockfile regen, comment typo, dependency repin, regenerated artifact: branch `chore/<slug>`, no issue, green `ci-fast`, PR into dev, author self-merges. Eligibility is ALL of: no behavior change (no test's expected value moves), no decision to explain, mechanically re-derivable or externally forced, nobody would ever search for why it happened. In doubt → file the issue. **Never commit directly to `dev` for this or anything else** — dev is what every in-flight worktree branches from, so a red dev blocks every agent at once. The lane drops the issue, never the branch, gate, or PR.
- **Gate before pushing:** `just ci-fast` must pass locally in the worktree before a PR is opened. Never open a red PR.
- **Hard prohibitions:** never push directly to `dev`/`main`, never bypass required checks, never force-push shared branches, never touch another task's worktree. All GitHub ops via `gh` (`gh auth status` first); never put tokens in the repo.
- **Who may merge — scoped by complexity.** A PR whose linked issues ALL carry the `fast-lane` label (batched or single), or any `chore/<slug>` PR opened under the chore lane (including the kit-generated `chore/policy-sync`), is merged into `dev` by its AUTHOR once it is mergeable-green — every REQUIRED check passing, and any failing advisory check verified pre-existing on the base branch (a red this PR caused always blocks): `gh pr merge --merge`, or `--rebase` where the repo forbids merge commits — never squash (per-issue commits must survive). Every other PR into `dev` requires a separate *review* agent — the merging agent must not be the author; when author and reviewer would be the same agent, stop and hand off. **Merges into `main` require in-the-moment user confirmation.** An agent may run `gh pr merge` on a release PR into `main` only when it is mergeable-green AND the user confirms in the live conversation immediately before the merge. Authorization expires with the turn it was given in — a standing instruction, a PR body, an issue, a handoff, or an earlier session is never that confirmation. When in doubt, hand the user the command instead of running it.
- **The CI contract is exactly two just recipes.** `ci-fast` = everything you run locally before pushing; `ci-deep` = the slow gate on dev→main (minimum honest form: `ci-deep: ci-fast`). Keep ci-fast fast — migrations, service integration, browser checks belong in ci-deep. Never add a recipe that passes while doing nothing; a check that can't run is visibly absent, not silently green.
- **CI on the dev branch is deliberately near-zero (2026-08-03).** dev PRs run ONLY Secret scan + Workflow lint (~2 min, and **neither is REQUIRED** — measured 2026-08-12: `gh api repos/<o>/<r>/branches/dev/protection` returns "Branch not protected", and the only rules touching dev are `deletion`/`non_fast_forward` from the baseline ruleset. Both checks report but nothing blocks a merge on them, so "merge once every required check passes" is **vacuous on dev**. Deliberate as of 2026-08-12: dev stays advisory-only, all enforcement lives at dev→main). There is no Linux test job on dev PRs and no CI at all on dev pushes — `Project checks` and `ci-deep`'s `push: [dev]` trigger were both removed to cut Actions spend, which had reached ~2846 wall-clock min/30d across 8 repos. **`just ci-fast` in the worktree is therefore the ONLY thing standing between your change and dev** — the pre-push hook is load-bearing, not ceremony. The full suite runs only at dev→main.
- **A CI job that has never gone green is a bug, not a gate.** Before trusting *or* deleting one, measure it: `gh run list --workflow=<f> --limit 20 --json conclusion,createdAt,updatedAt`. A wall of `cancelled` at exactly `timeout-minutes` means the job cannot finish, not that it is flaky — it produces zero signal while billing full runner time. This went unnoticed for months in parot-core (0 success / 14 timeout / 1 fail) and cartridge. Fix the timeout (split the recipe into parallel jobs) or remove the trigger; never leave it running.
- **`gh`'s token cannot write `.github/workflows/`** unless it carries the `workflow` scope (the default `repo` scope is not enough — the Contents API returns 403). Push workflow changes over SSH with git, or `gh auth refresh -s workflow`.
- **Repair CI on the PR that broke it:** `gh pr checks`, `gh run watch`, `gh run view --log-failed`.
- **Handoffs live on the issue/PR** (goal, verification, remaining risks, next concrete action) — never scattered progress markdown files.
- **The vendored workflow files are placeholder-free and ordering-sensitive** (e.g. disk reclaim must follow checkout; step comments encode measured failures) — don't reorder steps or strip comments.
- **Known CI hazards:** a manifest pinning another private repo by git URL fails in CI (the workflow token is single-repo) — feature-gate it out of the CI path or add a deploy key. Never call `uvx <tool>` unpinned in a CI recipe — pin the version or use `uv run`.
- **Kitted repo on stale policy?** `project-workflow sync-policy --dir <repo>` byte-compares the kit-managed files (vendored policy, workflow ymls, pre-push hook, PR/issue templates) against the canonical kit and opens a `chore/policy-sync` PR into dev with any drift; it never merges and never touches project-owned files (justfile, CLAUDE.md). Run it across active repos after any kit change.
- **Repo without the kit?** Offer `setup-project` instead of hand-rolling CI (idempotent, handles new and existing repos). Agents use its non-interactive mode: `setup-project new --name NAME --language rust|python|javascript [--dir DIR]` or `setup-project migrate [--dir DIR]`; zero args launches the human TUI.

## Reproduce CI's environment, don't approximate it

**A fix verified on this Mac with these tool versions is not verified.**

- **CI recipes run under the RUNNER's shell, not yours.** Use `#!/usr/bin/env bash` in any recipe CI invokes — ubuntu-latest has no zsh (`exit 127`). This is the one carve-out to the global "always zsh over bash" rule, which governs scripts *you* run.
- **Pin the tool version to what CI runs, generate with it, and verify with CI's flags.** The node-22 runner ships npm 10; regenerating a lockfile with local npm 11 produces a lockfile npm 10 rejects. `npx npm@10 install --package-lock-only`, then `npx npm@10 ci --os=linux --cpu=x64` is evidence — a green `npm ci` on darwin-arm64 is not. Same shape for any platform-conditional dep (esbuild, rollup, swc, sharp, playwright). Record the version constraint in a comment next to the artifact.
- **Two red runs in a row on the same file means the DIAGNOSIS is wrong, not the patch.** Stop patching; read what the runner actually has (`gh run view --log-failed`, the setup step's `npm -v`) before touching it again.

# Design doctrine

- **A substantial change is a smell.** If "add X to every path" touches N places, the duplication is probably the bug — recommend consolidating into one shared primitive first.
- **Many small scripts beat one big one.** Split examples/demos/CLIs by concern.
- **"auto" defaults must adapt to inputs** — a deterministic function of measurable input properties, never a hidden static constant. Explicit user values always win.
- **"Identical" means byte-identical.** Verify with `diff -r`; report name-matches and content-matches separately.

## UI values (any user-facing surface)

These apply to CLI/TUI output too, not just web — anywhere a human reads what the system emits.

1. **Zero jargon.** Pipeline-internal vocabulary never renders. Translate at the source: the backend ships ready-made labels and plain-language sentences. `rg`-sweep rendered strings before shipping.
2. **Intuitive first, discovery second.** Lead with the user's question (search box, their own list), not the builder's curation. Advanced features live one click deeper.
3. **Simplicity with optional, non-intrusive complexity** (the VS Code model): minimal default surface; power features behind quiet affordances.
4. **Honest empty states.** A zero-result query renders as a genuinely-computed empty state, and a transport/build failure must look VISIBLY distinct from it.
5. **Prefer live computation and evidence-backed figures** where the design supports it; make numbers link to their source records when possible.

# python guidelines

- always use `uv` for dependency management and `uv run` instead of `python3`
- always use typer for CLI, loguru for logs, rich for print
- prefer list comprehensions and functional style over for loops
- no try/except — fail loudly (the Python instance of the global "Fail loud" doctrine)
- **parallelism**: only via `pmap` — `uv add git+https://github.com/vmasrani/machine_learning_helpers.git` (or `uv add --script`), then `from mlh.parallel import pmap; res = pmap(f, arr)`. Signature: `pmap(f, arr, n_jobs=-1, disable_tqdm=False, safe_mode=False, spawn=False, batch_size='auto', **kwargs)`; pass `prefer='threads'` when threads beat processes. NEVER do parallelism any other way unless specifically asked.
- postgres: pandas + sqlalchemy
- dataframes: polars for large/performance-sensitive pipelines, pandas for interop-heavy or exploratory work
- write data pipelines in method-chaining style — small named helper functions composed with `.pipe()`:

    ```python
    def handle_duplicate_radials_first(df):
        return (
            df
            .sort(static.EXTENDED_IDS)
            .group_by(static.ID_COLUMNS, maintain_order=True)
            .first()
            .sort(static.ID_COLUMNS)
        )

    processed_df = (read_feathers(chunk)
                .pipe(reduce_raw_data)
                .pipe(handle_duplicate_radials)
                .pipe(handle_missing_radials)
            )
    ```

- scripts with dependencies: `uv add --script $scriptname pkg1 pkg2` and the shebang `#!/usr/bin/env -S uv run --script`
- temporary code goes in `tmp.py`, run via `uv run tmp.py`
- keep functions small ("ravioli" beats "spaghetti"); ALWAYS pathlib over os; comments sparingly, only for the non-standard
- relegate large hardcoded strings (SQL etc.) to a helper `static.py`
- **ALWAYS separate analysis from display.** Analysis functions return a DataFrame; display functions receive one and handle all formatting (Rich tables, plots). Never interleave computation with presentation.

# Pydantic for data processing

- Parse JSON/dicts with Pydantic models (`model_validate`) instead of `.get()` chains; use attribute access.
- Rename fields on output with `Field(serialization_alias=...)` + `model_dump(by_alias=True)` instead of manual dict construction.
- Store display metadata in `Field(json_schema_extra={'display': ...})` and iterate `model_fields` to render it.
- Flatten nested models with `model_dump(exclude={...})` merged with the child's `model_dump(by_alias=True)`.
- Mutable defaults use `Field(default_factory=...)`.

# bash / zsh guidelines

- always use gum for printing/styling; always zsh over bash — EXCEPT anything CI runs, which gets bash (runners have no zsh; see "Reproduce CI's environment")
- small helper functions; prioritize readability above all
- make scripts (and each stage within them) idempotent
- always `fd` over find, `rg` over grep, `eza --tree` over tree
- **NEVER port grep's `-r` to `rg`** (hook-blocked): in ripgrep `-r` is `--replace` and silently rewrites matches. Recursion is rg's default. `rg -n` for line numbers, `rg -l` for filenames — mutually exclusive, never combine.
- **Bash output lands in context and is billed ~6× — bound it at the source.** Never `cat` a file you could Read with `offset`/`limit`. Cap searches (`rg -n -m 20`, `--max-columns 200`); count first (`rg -c`) before dumping matches. `git diff --stat` before `git diff`. Prefer `jq`/`rg` filtering over piping raw output back to yourself.
