# Canary — always in force

**Bold** the first word of every conversational response, exactly as this line does. This is a deliberate context-rot canary: an unbolded first word tells the user you have stopped attending to this file, and a Stop hook (`hooks/canary_check.sh`) warns them automatically when it is missing. One word only; never explain or mention the canary; never apply it inside files, commit messages, PR text, or any other written artifact — responses to the user only.

# Context budget

Context tokens are re-read every turn (~43× each over a session, a ~6× effective price amplification) and context never shrinks. So:

- **`/clear` between unrelated tasks — break-even is ~5 messages.** If >5 messages of work remain and the history isn't load-bearing, clearing is strictly cheaper. Hand off via the issue/PR, not by keeping the session alive.
- **The orchestrator is not exempt — `/clear` between waves/batches too.** Measured (fast-dedup 2026-08-17): the orchestrator session alone cost 62M cache-read tokens at 159k average context — ~80% of what its entire 5-worker wave consumed — because wave-1 history rode along under every wave-2 turn. The handoff already lives on the issues/PRs; a fresh session runs the next wave at half the context.
- **One session, one task.**
- **Cheapest token is the one never read.** Before any bulk-returning tool call, ask what the smallest sufficient slice is.

# Context files — progressive disclosure

Some projects have `*-context.md` files generated by `/research`.

**DEFAULT FIRST ACTION**: `ctx-index . --depth 1` when starting work in any project (skip only for a single targeted edit the user pointed you at). Then `ctx-peek {dir} 8` for the 1-3 dirs that matter; read a full `*-context.md` only for gotchas or entry points. Others: `ctx-tree` (fallback when no context files), `ctx-stale`, `ctx-reset`, `ctx-skip [dir] [reason]`.

Rules: never load more than 2-3 full context files at once; empty `ctx-index` → fall back to `ctx-tree`; stale → suggest `/research`.

# Code navigation — prefer LSP

When LSP plugins are enabled, prefer LSP tools (`definition`, `references`, `diagnostics`, `hover`, `symbols`) over grep/glob. After every file edit, check LSP diagnostics and fix introduced errors in the same turn.

- **Never re-Read a file already in this session's context.** Edit/Write error on failure, so re-reading to "verify" is pure waste. Re-read only when an *external* process changed the file.

# Fail loud — never write slow defensive fallbacks

**There is ONE correct (fast) path. When it can't run, stop with a loud, actionable error — NEVER silently fall back to a slow, degraded, or wrong path.** Applies in every language; prefer a crash over a plausible-but-wrong result.

- **The fast path is the only path.** Delete old slow implementations and any env var/flag that silently re-enables a degraded mode.
- **Failures error loudly** (nonzero exit / raise / `Err` / throw) with an actionable message naming what failed and how to fix it. Never return unfiltered, empty, partial, or wrong-but-plausible results.
- **Validate invariants up front** — fail before doing work, not mid-flight.
- **Stub the not-yet-implemented loudly** — explicit "not implemented" error, never a fall-through to an older path.
- **A test that cannot run is SKIPPED VISIBLY** (`#[ignore]` / `pytest.skip` / `t.Skip`) — "skipped" and "passed" must never be the same observable state.
- **Nuance:** a legitimate absence (`NotFound`, empty `Option`) may return quietly. The test: "could the caller mistake a failure for success?" If yes → fail loud.
- **No try/except / try/catch for control flow.** Catch only to add context and re-raise, or at a genuine top-level boundary (CLI entrypoint, request handler).

# Fable is an orchestrator — Fable NEVER writes code

**HARD RULE — when the session model is Fable, Fable NEVER writes, edits, or patches code — not scripts, not tests, not one-line fixes, not code smuggled through Bash heredocs. ALL code is written by opus/sonnet/haiku subagents (Agent tool or Workflow `agent()`).** Fable scopes, researches, designs, writes precise self-contained prompts, dispatches subagents, reviews their diffs, and integrates. Fable may still directly write non-code text: plans, prompts, reviews, documentation, commit messages, memory/context files.

# Delegate context-heavy reads — applies at every session model

Subagents start at ~34k and stay small; the main session sits at 175k. Anything that **reads a lot and returns a little** belongs in a subagent — the bulk never enters your context.

- **Always delegate:** CI log triage (`gh run view --log-failed`), test-failure diagnosis, cross-worktree file scouting, "which file does X", doc/API research.
- **Parallel by default.** The bar is "could this run concurrently?", not "was I told to parallelize?". Pre-stage work while agents run.
- **Verify, don't trust.** Subagent self-reports are claims, not evidence. For load-bearing work verify yourself: `git status`/`git diff`, build, run the FULL suite (not the agent's chosen subset).
- **Prefer a fresh agent with a self-contained prompt over a fork** — a fork inherits the whole 175k context and saves nothing.
- **Close out idle agents** with `TaskStop({task_id: "<agent-name>"})` when their thread is genuinely closed; sweep at the end of any spawning turn. But don't stop an agent whose context you might still want — `SendMessage` reuses its research; respawning pays again. Idle agents don't burn tokens; this is roster hygiene, not cost saving.
- **Default known-slow commands to `run_in_background: true` up front** — full test suites, `cargo`/`just` build-and-test recipes, `queue`/`testq`, CI watches (`gh run watch`), anything with a "queue wait + suite time" shape. There is no auto-background setting in Claude Code (checked 2026-08-14) — this is a standing habit, and it must be stated explicitly in delegation prompts, since fresh subagents don't inherit this file.
- **Never spend a turn polling.** Tracked background work re-invokes the session on completion; a `queue -l`/`git log` status-poll turn buys nothing and re-reads the full context (~159k) to do it. Poll only external state the harness can't see, and batch it with real work.
- **Mandate terse structured reports in every dispatch prompt** — ≤12 lines: SHA / exact counts / conflicts resolved / anything left undone. A worker's report lands in the orchestrator's context and is re-read every turn thereafter; prose narratives compound forever.
- **Put a context-hygiene line in every dispatch prompt** (bounded Reads, `rg -n -m 20` caps, batch independent tool calls, never re-read). Measured: wave workers averaged 100–126k context — ~70–90k of avoidable file/tool output on top of their 34k start — and cost scales as turns × context.

# Model selection for subagents — Opus 5 is BANNED

**Fable orchestrates; the ONLY worker models are Opus 4.8 (`claude-opus-4-8`) and Sonnet 5 (`claude-sonnet-5`), with Haiku for trivia. "opus" ALWAYS means Opus 4.8 — the `opus48-worker` agent pins it explicitly. Opus 5 is NEVER used — not as a worker, not as an orchestrator, not as a session model — with exactly one exception: the user explicitly requests it in the live conversation.**

- trivial (scouting, file mapping, mechanical edits) → `haiku`
- simple tasks, and ALL research-type subagents (context files, codebase exploration, doc fan-outs) → `sonnet` (haiku for the most trivial scouting)
- moderately difficult (standard implementation, code review, test writing) → `opus` (4.8)
- very difficult → `opus` (4.8) with max reasoning effort

**Grade per FEATURE, not per wave.** In a multi-feature batch, each worker gets its own model: opus (4.8) only where the algorithmic seam is genuinely tricky; `sonnet` (~1/5 the price) for adapters, I/O plumbing, format/spec-following code, and scaffolding. Measured (2026-08-17): a 5-feature wave ran all-opus when at least 2 features were sonnet-shaped — ~30-40% of worker cost for no quality gain.

**HARD RULE — always pass `model` explicitly on every subagent; never `model: fable`, never let a subagent silently inherit the session model.** Scale reasoning effort to task difficulty.

# Rust builds — the job queue (`queue`)

**Add the `queue` prefix yourself** on `cargo test|nextest|bench|miri` and `just test*|bench*|ci-fast|ci-deep` — nothing rewrites your command; a PreToolUse hook only DENIES unqueued ones. `queue X` behaves exactly like `X` (waits for a free slot, streams live output, returns X's own exit code). Leave `cargo check|clippy|build` and `just lint*` unqueued — that's what keeps them instant.

- Compound commands go as ONE quoted string — `queue 'cd /repo && cargo test'`, never `queue cd /repo && cargo test` (the shell splits on `&&` first).
- A pause before output is the QUEUE, not a hang — check `queue -l`, never re-run. Run long suites detached (`run_in_background`).
- `| tail` destroys the exit code — read `queue --exit-code --last` before claiming a pass.
- Agents write, the lead builds — ONE process compiles and runs the suite.
- Everything else — cancel/`--triage` semantics, SJF jumping, `--solo`, slots, coalescing, the settled don't-re-investigate list: `~/dotfiles/maintained_global_claude/queue-reference.md`.

# Cargo — never compile the same dependency twice

sccache is wired machine-wide (`~/.cargo/config.toml` → `rustc-wrapper`): dependency crates compile once per (crate, rustc, flags) across ALL repos and worktrees; workspace crates stay incremental per target dir. On a machine where `command -v sccache` fails, install it and add the wrapper line before any Rust work.

- **One worktree per batch** (see Implementation batching) — N worktrees × cold `target/` is where the remaining rebuild time goes.
- **Never `cargo clean` to "fix" a problem** — it discards hours of workspace compilation on a hunch. The sanctioned forced rebuild (test count went DOWN → binary lacks your code) is `cargo clean -p <crate>` scoped to the suspect crate, never a full wipe.
- **Keep flags stable.** Ad-hoc `RUSTFLAGS`, feature-set changes, and profile edits invalidate caches tree-wide; flags live in `.cargo/config.toml`/justfile, never per-command env vars.
- **Pin the toolchain** (`rust-toolchain.toml`) so sibling worktrees don't silently rebuild the world on rustc drift.
- **Settled — don't re-investigate a shared `CARGO_TARGET_DIR` across worktrees:** cargo's target-dir lock would serialize the unqueued `check`/`clippy` calls that are kept instant on purpose; sccache already de-dupes the expensive part without lock contention.

# Evidence discipline — a green is a claim, not proof

These rules target failures that produce confident, plausible, wrong output. Some are hook-enforced; the hook's presence doesn't excuse the habit.

- **Reconcile the test COUNT against an explicit baseline every run** (e.g. `main @ 4ee8817 = 1502`). A count that goes DOWN without deletions means the binary doesn't contain your code — force a rebuild.
- **Never read a summary line as proof.** Grep explicitly: `rg -n 'FAIL|test run failed|^error'`.
- **Never pipe a test or build run** — `cmd | tail` exits with tail's status. Capture in full, and **end the command with the run's own status, never with an `echo`**:

      <cmd> > /tmp/run.log 2>&1; rc=$?; echo "exit=$rc" | tee -a /tmp/run.log; exit $rc

  The `echo "exit=$?"`-only form leaves the SHELL exiting 0, and a `run_in_background` completion notification carries only that process status — it will announce success for failed runs (bit three background `ci-fast` runs in one session). The trailing `exit $rc` is the entire fix; a `( … )` subshell does not help.
- **A background task's reported exit code is the wrapper's, not the command's.** Never accept it over the log; grep the log for both the status line and the failure patterns.
- **Extract from a captured log with `rg -n 'FAIL|error'` — never `cat` it, never Read it whole, never read it twice.** A captured log is a re-queryable file on disk, not something to park in context.
- **Verify a test filter selected what you think.** A pass over zero tests is a pass. Prefer positional filters; with `-E` expressions, confirm a non-zero expected count first.
- **Anchor the working directory.** Absolute `cd` at the head of every build command, or prefix `pwd &&`.
- **A conditional action needs a conditional marker.** `git commit; echo done` prints the marker even when nothing committed. Compare `git rev-parse HEAD` before/after, or guard: `git diff --cached --quiet || git commit`.
- **Re-run the full suite on the MERGED result** — per-branch greens don't cover the combination.

# Workflow defaults

- **Red-green TDD stays the rule for bug fixes and core-invariant changes** — the reproducing test IS the spec: write it first, watch it fail. Multi-feature work follows "Implementation batching" below: tests written per feature, executed ONCE on the merged batch.
- **Verbal plan approval counts.** If ExitPlanMode is rejected but the user says "proceed" / "go ahead", start executing immediately.
- **Use git worktrees for non-trivial implementation work.** For path-dep'd sibling repos, create matching worktrees under one parent dir so relative deps resolve.
- **Never build in, or `cp` out of, a tree another session has uncommitted work in** — check `git -C <tree> status --porcelain` first. Relocate changes with `git stash` / `git diff | git apply` scoped to files you actually modified.
- **Git cleanup is local-only by default.** Never delete remote branches or unmerged work unless explicitly told.

# Implementation batching — one comprehensive test round per batch

**Default for multi-feature work (2+ separable features in one repo): implement the whole batch — F1 → … → F6 — then ONE comprehensive test round on the merged result.** Per-feature test rounds pay queue wait + build + suite + log triage N times to prove partial states that never ship; the merged result is the only thing that ships, and it needed its own full run anyway.

- **Freeze the seams first.** Before dispatching parallel feature agents, fix the shared types/traits/schemas in a short design pass. Batching is safe only when features compose through agreed interfaces; a feature that must *change* a shared seam leaves the batch and lands first, alone.
- **Tests are WRITTEN per feature, just not RUN per feature.** Every feature ships with its tests in the same commit — happy path, boundaries, failure modes. Deferred execution, never deferred authorship: "one test round at the end" must never decay into "write the tests at the end".
- **Static gates stay per-feature:** `cargo check` + `clippy` (unqueued, instant) green before a feature agent reports done. A compile error caught per-feature costs nothing; caught at merge it entangles six diffs.
- **One worktree per batch, not per feature.** Parallel agents partition by file/module ownership, declared in each dispatch prompt — disjoint files mean no conflicts and ONE target dir instead of N cold ones.
- **One commit per feature → one branch → ONE PR, reviewed once.** In kitted repos, file ONE issue scoped to the batch with a per-feature checklist (the feature-work analogue of a fast-lane batch). When the test round goes red, attribute mechanically — per-feature commits make `git bisect` / single-commit revert pinpoint the culprit; never hand-debug the union.
- **The one round is: full suite on the merged result — queued, detached, count-reconciled, run ONCE, by the agent who MERGES.** "One round" binds the reviewer too: when author≠merger, the integrator does merges + static checks only, and the merger runs the single full gate with its own eyes before merging. Never two identical full gates on the same SHA (measured: integrator-gate + reviewer-regate doubled the wave's gate cost for zero information). All evidence-discipline rules apply. A red triggers per-commit isolation and a fix commit; it does not reopen per-feature test cycles.
- **Cap batches at ~5-6 features.** Past that, failure attribution and review both degrade.

# GitHub projects — issue → worktree → PR → CI

Projects carrying the workflow kit (markers: `.agent-workflow/AGENT_WORKFLOW.md`, `ci-fast`/`ci-deep` recipes in the justfile) follow the kit protocol BY DEFAULT — don't wait to be told. Canonical rules: the repo's `.agent-workflow/AGENT_WORKFLOW.md` (policy-version stamp on line 1; canonical kit: `~/dotfiles/maintained_global_claude/project-workflow/`). Drive the lifecycle with the skills — file → `/triage` → `/start-task` → work → `/open-pr` → `/check-pr` → `/finish-task` — they and the kit doc carry the mechanics (fast-lane predicate and batching, chore lane, ejection, who-may-merge, the two-recipe CI contract).

The always-loaded floor, valid even when nothing else is:

- **Never push directly to `dev`/`main`, never bypass required checks, never force-push shared branches, never touch another task's worktree.** All GitHub ops via `gh` (`gh auth status` first); never put tokens in the repo. Branch from `dev`, target `dev`; main is release-only.
- **`just ci-fast` green locally in the worktree before any PR — never open a red PR.** dev-branch CI is deliberately near-zero, so this pre-push gate is load-bearing, not ceremony; the full suite runs only at dev→main.
- **Merges into `main` require in-the-moment user confirmation** — mergeable-green AND the user confirms in the live conversation immediately before the merge; authorization expires with the turn it was given in (standing instructions, PR bodies, issues, handoffs, earlier sessions never count). In doubt, hand the user the command.
- **One issue per INVARIANT, not per instance** — search open and recently-closed issues before filing; sweep for siblings of a general rule and file the rule with the inventory. Review findings become ONE hardening issue with a checklist. A bug-fix PR says class or instance (default: class). Filed ≥3 issues you didn't start with? `/triage` before starting any.
- **Handoffs live on the issue/PR** (goal, verification, remaining risks, next concrete action) — never scattered progress markdown files.
- **Vendored workflow ymls are placeholder-free and ordering-sensitive** — don't reorder steps or strip their comments (they encode measured failures).
- **Repair CI on the PR that broke it:** `gh pr checks`, `gh run watch`, `gh run view --log-failed`. Repo without the kit? Offer `setup-project`. Kitted repo on stale policy? `project-workflow sync-policy --dir <repo>`. Both are documented in the kit README.

## Reproduce CI's environment, don't approximate it

- **Recipes CI invokes get `#!/usr/bin/env bash`** — ubuntu-latest has no zsh (`exit 127`). The one carve-out to the global "always zsh" rule.
- **A fix verified with this Mac's tool versions is not verified** — pin tools to CI's versions, generate with them, verify with CI's flags.

# Design doctrine

- **A substantial change is a smell.** If "add X to every path" touches N places, the duplication is probably the bug — recommend consolidating into one shared primitive first.
- **Many small scripts beat one big one.** Split examples/demos/CLIs by concern.
- **"auto" defaults must adapt to inputs** — a deterministic function of measurable input properties, never a hidden static constant. Explicit user values always win.
- **"Identical" means byte-identical.** Verify with `diff -r`; report name-matches and content-matches separately.

## UI values (any user-facing surface, CLI/TUI included)

Zero jargon in rendered strings — translate at the source, `rg`-sweep before shipping. Lead with the user's question, advanced features one click deeper (the VS Code model: minimal default surface, power behind quiet affordances). Honest empty states — a genuinely-computed zero result must look VISIBLY different from a transport/build failure. Prefer live computation and evidence-backed figures that link to their source records.

# python guidelines

- always `uv` for dependency management and `uv run` instead of `python3`
- always typer for CLI, loguru for logs, rich for print
- prefer list comprehensions and functional style over for loops
- no try/except — fail loudly (the Python instance of "Fail loud")
- **parallelism**: only via `pmap` — `uv add git+https://github.com/vmasrani/machine_learning_helpers.git` (or `uv add --script`), then `from mlh.parallel import pmap; res = pmap(f, arr)`; pass `prefer='threads'` when threads beat processes. NEVER do parallelism any other way unless specifically asked.
- postgres: pandas + sqlalchemy; dataframes: polars for large/performance-sensitive pipelines, pandas for interop-heavy or exploratory work
- write data pipelines in method-chaining style — small named helpers composed with `.pipe()`:

    ```python
    def handle_duplicate_radials_first(df):
        return (df.sort(static.EXTENDED_IDS)
                  .group_by(static.ID_COLUMNS, maintain_order=True)
                  .first()
                  .sort(static.ID_COLUMNS))

    processed_df = (read_feathers(chunk)
                    .pipe(reduce_raw_data)
                    .pipe(handle_duplicate_radials)
                    .pipe(handle_missing_radials))
    ```

- scripts with dependencies: `uv add --script $scriptname pkg1 pkg2` and the shebang `#!/usr/bin/env -S uv run --script`
- temporary code goes in `tmp.py`, run via `uv run tmp.py`
- keep functions small ("ravioli" beats "spaghetti"); ALWAYS pathlib over os; comments sparingly, only for the non-standard
- relegate large hardcoded strings (SQL etc.) to a helper `static.py`
- **ALWAYS separate analysis from display.** Analysis functions return a DataFrame; display functions receive one and handle all formatting (Rich tables, plots). Never interleave computation with presentation.

# Pydantic for data processing

- Parse JSON/dicts with `model_validate` instead of `.get()` chains; use attribute access.
- Rename fields on output with `Field(serialization_alias=...)` + `model_dump(by_alias=True)`, not manual dict construction.
- Store display metadata in `Field(json_schema_extra={'display': ...})` and iterate `model_fields` to render it.
- Flatten nested models with `model_dump(exclude={...})` merged with the child's `model_dump(by_alias=True)`.
- Mutable defaults use `Field(default_factory=...)`.

# bash / zsh guidelines

- always gum for printing/styling; always zsh over bash — EXCEPT anything CI runs, which gets bash (see "Reproduce CI's environment")
- small helper functions; readability above all; make scripts (and each stage within them) idempotent
- always `fd` over find, `rg` over grep, `eza --tree` over tree
- **NEVER port grep's `-r` to `rg`** (hook-blocked): in ripgrep `-r` is `--replace` and silently rewrites matches; recursion is rg's default. `rg -n` for line numbers, `rg -l` for filenames — mutually exclusive, never combine.
- **Bash output lands in context and is billed ~6× — bound it at the source.** Never `cat` a file you could Read with `offset`/`limit`. Cap searches (`rg -n -m 20`, `--max-columns 200`); count first (`rg -c`) before dumping matches. `git diff --stat` before `git diff`. Prefer `jq`/`rg` filtering over piping raw output back to yourself.
